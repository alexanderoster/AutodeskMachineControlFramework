AMCF UI Evolution Plan

Goal: define a cohesive next-generation widget architecture for robust HMI design, with a dedicated and expandable form module and clear compatibility path from the current AMCF schema.

Status update (2026-02-23): phase-1 foundation work is substantially complete. All 12 former content-item types are now first-class modules in both backend (CUIModule_ContentLeaf) and frontend (AMCModule_Factory.vue component map). The /ui/* routes were retired in favor of dedicated /api/* handlers (CAPIHandler_UI is unregistered). The v2 frontend state model via /api/frontend is operational, and /api/state is deprecated with a migration warning. The client supports both v2 and legacy formats through _normalizeV2ToLegacy() and ContentLeaf unwrapping. Remaining phase-1 items are cross-cutting property standardisation, shared table base, and runtime schema validation.

1. Target Architecture Principles

Schema-First Widgets

Every widget should be declared by typed JSON schema with stable contracts and backward-compatible defaults.

Composable Layout

Widgets should nest cleanly under grid, tabs, dialogs, and future split panes without custom one-off logic.

Unified Event Model

All widgets should emit strongly typed events with context, source widget UUID, and value payload schema.

Responsive by Default

Desktop/wall-panel/mobile behavior should be explicit in widget properties and visible in a form/page builder preview mode.

4. Dedicated Form Module Vision

The form module is now a first-class module (promoted from content item via CUIModule_ContentLeaf). It supports v2 frontend updates and renders through AMCModule_Form.vue. Entities support disabled, readonly, changeevent, and basic validation (double range, string length). The next step is to expand its field types, add a layout engine, sections, and workflow capabilities.

Current entity types: edit, switch, memo, combobox Current validation: double (min/max), string (length) Target entity types: 20+ Builder + Runtime parity Responsive section/grid layouts

7. Migration and Delivery Plan

Phase 1: Stabilize Existing Widgets (Low Risk, High Value)

  • Completed: migrate client traffic from /ui/* to dedicated /api/* handlers and unregister CAPIHandler_UI.
  • Completed: promote all 12 former content-item types (paragraph, image, chart, videostream, upload, buildlist, executionlist, alertlist, buttongroup, parameterlist, configurationlist, form) to first-class modules in backend (CUIModule_ContentLeaf) and frontend (AMCModule_Factory.vue component map).
  • Completed: implement v2 frontend state via /api/frontend handler with frontendWriteItemToJSON/frontendWriteModuleStatusToJSON; mark /api/state as deprecated with migration log warning.
  • Completed: add v2 format normalisation (_normalizeV2ToLegacy()) and ContentLeaf unwrapping in client so both legacy and v2 payloads render correctly.
  • Completed: implement ModuleFactory pattern in Vue 2 client, replacing ContentLeaf abstraction with direct component resolution by module.type.
  • Completed: v2 widget support for chart, image, form, parameterlist, configurationlist, logs, graphic, glscene, layerview, and custom modules.
  • Standardize cross-cutting properties (visibleWhen, enabledWhen, events, styleTokens).
  • Fix known form/list issues (string validation, alert row mapping, configuration action schema usage).
  • Create a shared tableplus base and migrate parameterlist, alertlist, buildlist, executionlist, configurationlist.
  • Add runtime schema validation to catch malformed module payloads before rendering.

Phase 2: Introduce Form as First-Class Module

  • Promote form from content item to module-level citizen with its own layout engine and section model.
  • Add new field types (number, slider, date/time, file, multiselect, signature, calculated).
  • Implement validation engine with field/cross-field/form layers and server async hooks.
  • Provide form action bar with optimistic/pessimistic submit policies and dirty-state handling.

Phase 3: Form Builder + Advanced HMI Modules

  • Ship formbuilder authoring UI with schema export and preview.
  • Add advanced modules: wizard, statusmatrix, alarmcenter, splitview, timeline.
  • Provide template packs for common AM workflows (job setup, execution monitoring, maintenance).
  • Introduce policy packs (role gates, confirmation patterns, audit requirements).

8. Technical Decisions to Lock Early

DecisionRecommendationImpact
State transport model Done: v2 frontend schema/event model is primary via /api/frontend; dedicated /api/* handlers replace /ui/*; /api/state deprecated with log warning. Client supports both v2 and legacy via _normalizeV2ToLegacy(). Cleaner data flow, fewer race conditions, and a path to remove legacy compatibility code.
Module factory model Done: Vue 2 client uses AMCModule_Factory.vue component map (20 types); C++ backend uses CUIModuleFactory::createModule() with CUIModule_ContentLeaf wrapper for leaf types. Uniform module instantiation, simpler rendering pipeline, no container dependency for leaf types.
Schema governance Define JSON schema versions and compatibility policy (schemaVersion). Safe rollout of new widgets and properties.
Design tokens Current: Vuetify light theme colors applied from /api/config response. Next: create centralized token map (spacing, typography, colors, state tones). Consistent HMI look and fast theme changes.
Event naming convention Current: ad-hoc event names (changeevent, selectevent, loadconfiguration, etc.) via /api/event. Next: namespace all events (module.action.intent) with payload schema docs. Easier backend contract maintenance and tracing.
Builder storage Store generated schemas as versioned server artifacts with diff/audit. Traceable HMI evolution and rollback safety.

9. Success Criteria

  • New full-featured form screen can be built in schema/builder without custom page code.
  • One responsive form definition supports desktop + panel + tablet layouts.
  • Widget event contracts are typed and documented; no ad-hoc payload guessing.
  • At least 80% of current custom one-off table/list logic replaced by shared base modules.
  • Operator-critical actions support role checks + confirmation + audit context.

Result: cohesive, scalable HMI architecture with lower maintenance cost and faster screen delivery.

10. Content Module Deprecation Plan (Concrete)

Goal: deprecate the monolithic content container and promote each content item type to a first-class module with its own schema, lifecycle, and API contract.

Target: pages/dialogs/custom pages contain only proper modules (for example paragraph, image, chart, form, buildlist, executionlist, alertlist, parameterlist, configurationlist, upload, videostream, buttongroup).

Current state (2026-02-23): steps 1–5 are substantially complete. All 12 leaf types have backend and frontend first-class support. Legacy <content> XML is still used in all Example configs (LPBFSystem, ScanlabOCM, NAVASTO, Rapture). The EnableLegacyContentModule feature flag is not yet implemented. No XML migration tooling exists yet.

Compatibility window: preserve legacy content parsing behind a feature flag until all machine definitions are migrated.
